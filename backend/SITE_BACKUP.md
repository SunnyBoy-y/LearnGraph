# 全站备份与恢复

设置 → 数据与存储 → 全站备份与恢复。只有系统管理员可下载、校验和暂存全站备份；普通成员和工作区管理员均无权操作。每次操作在服务端验证当前管理员密码，失败限流；旧 GET 下载接口已经关闭。

下载时设置独立备份密码（至少 12 位）。整个内容使用 scrypt 派生密钥和 Fernet 认证加密，ZIP 里只可见加密格式说明与密文；API Key 不会以明文出现在可直接解压的文件里。请单独保存备份密码，丢失后无法恢复。

备份内容：

- SQLite 在线一致性快照或 PostgreSQL 原生一致性快照：全站所有用户、工作区、权限、业务记录、模型配置和凭据、二进制字段、历史配置均完整保存。数据库类型由实际生效的主库指向确定，迁移后不会备份已封存的 SQLite。
- 默认本地 storage 和 memory 下所有文件，包括 Memory 恢复密钥；数据库引用的上传文件逐个验证大小与 SHA-256。
- 实际生效的 Settings、全部 LEARNGRAPH_ 环境变量、启动目录的 .env 原文（如存在）、已配置的桥接／sandboxd／更新令牌文件。
- 持久化的沙箱镜像选择、初始化策略、镜像源与预览配置。
- 使用 OS Keyring 时保存当前及历史版本主密钥和可用的 identity key，恢复到独立 Keyring 命名空间。

支持本地 SQLite、主业务 PostgreSQL 和默认本地对象存储。Docker 镜像包含 PostgreSQL 18 的 `pg_dump`、`pg_restore`、`psql`，也支持已配置的外部 PostgreSQL 主库；其他数据库、活动 MinIO 或自定义存储根目录会明确拒绝，避免生成不完整的全站包。主库应使用专用 schema；额外的自定义 schema 会被拒绝。外部服务、运行中的沙箱磁盘、源码和容器镜像需要各自的备份。数据库快照是事务一致的；文件目录无法与数据库跨介质原子冻结，建议先停止任务和写入再下载。文件丢失、校验失败、链接逃逸或超限都会报错。

恢复流程：

1. 管理员上传加密 ZIP，输入当前管理员密码和备份密码。服务端解密，校验 ZIP 路径、去重、解压总量、清单、SHA-256、数据库完整性和外键，成功后只暂存原始密文。
2. 停止所有 API 实例、worker、定时任务及其他数据库写入方。在 backend 目录、原部署相同的 Python 环境执行页面给出的命令：

   ```text
   python -m app.services.site_restore --backup "页面显示的路径.zip" --server-stopped
   ```

3. 工具以隐藏输入读取备份密码；全站数据库和两个受管目录会被覆盖，数据库路径及 storage/memory 目标沿用当前实例位置。本机有效配置写入当前目录 `.env`；Docker 默认写入持久卷中的 `/data/restored.env`，应用及更新后的容器自动读取，进程环境变量仍有更高优先级。使用 `--env-file` 可指定其他目标文件，但必须确保启动时实际读取该文件。原数据库、目录、配置的恢复前副本会保留；应用失败会尝试回滚。
4. 启动／容器的环境变量优先于 .env。工具检测到冲突会在改动数据前拒绝执行，并只列出变量名；需先同步部署配置、从无冲突的终端重试。配置中的外部服务地址和令牌文件路径需要在目标主机上仍然可用。重启并使用备份中的账户重新登录，旧登录会话已撤销。

PostgreSQL 恢复会保留当前目标连接和当前单向迁移身份，不导入备份来源机器的数据库地址。恢复 SQL、逐表行数与内容摘要、外键/索引检查、历史会话撤销和激活身份修复在单个数据库事务中提交；校验失败则回滚。原生工具使用私有 libpq 凭据文件，不把密码放进进程命令行。备份包仍使用独立备份密码整体加密；原有 SQLite 备份包保持兼容，但 PostgreSQL 实例禁止应用 SQLite 包。

Docker 自动生成并从数据卷加载的主密钥可随恢复包一起恢复，同时重新加密当前 PostgreSQL 指向；显式写入容器环境变量的密钥仍需管理员同步，不能被备份静默覆盖。恢复保持当前数据根目录与数据库目标。

文件与配置使用持久恢复日志，数据库最后提交。若恢复进程被中断，服务启动会拒绝不确定状态。保持停服，使用相同镜像和数据卷执行：

```text
python -m app.services.site_restore --recover-pending --server-stopped
```

恢复工具依据数据库事务中的恢复标记完成恢复，或还原文件/配置；不会回退 SQLite。Docker 中可使用 Compose 一次性应用容器执行恢复（停止 app 内的主站与预览，以及所有 worker；数据库继续运行）。旧拓扑仍有独立 preview 容器时也必须停止它。只读挂载的令牌与备份内容一致时保持挂载不变；不同内容应先由管理员同步宿主配置。

Docker 操作示例（另有 worker 时也必须先停止）：

```text
docker compose stop app egress-proxy
docker compose run --rm --no-deps app python -m app.services.site_restore --backup /data/site-restore/页面中的任务.zip --server-stopped
docker compose start app egress-proxy
```

自动更新仍可在 PostgreSQL 下启用。独立宿主更新器在替换镜像前，对实际主库生成并校验原生备份并核对宿主副本 SHA-256；该更新备份含敏感恢复材料，只保存在更新器的 private 目录，不通过下载 API 暴露。用户下载的全站包与更新器的私有数据库包用途不同。更新、手动镜像回退、失败自动回滚及更新器重启恢复均验证 PostgreSQL 身份；镜像回滚不恢复旧数据库快照，保留升级后数据。缺少 `io.learngraph.primary-database=sqlite-postgresql-v1` 能力标记的镜像不能接管已激活的 PostgreSQL。

`--server-stopped` 是操作者对已停服的确认，不会自动关闭其他进程。不要在生产运行中执行覆盖恢复。恢复前副本也包含敏感信息，应由管理员保管。页面“校验并暂存”不代表全站数据已恢复。

默认上限为 `LEARNGRAPH_MAX_BACKUP_BYTES`（16 GiB），分别约束上传密文与解压后的数据总量，最多 100,000 个成员。数据库、附件、压缩和 Fernet 加解密均通过 1 MiB 分块和私有临时文件处理，保持旧加密格式兼容；不会将整库或整包读入内存。完整 HMAC、清单、SHA-256 和数据库检查通过后才允许恢复。数据库迁移的复制和增量重放批次同时受 500 行及约 8 MiB 字节预算约束；大事务分块执行和校验，但目标事务与捕获进度仍一起提交，任一块失败则全部回滚。

全站包及上传文件在数据根目录的 `.backup-work` 下暂存，更新快照使用迁移状态目录的 `maintenance-work`，更新待取出的 ZIP 也写入 `/data/.backup-work`。失败和下载结束（包括连接断开）时清理，避免大库占满容器 `/tmp` 或其内存文件系统。恢复接口在解析大文件前验证系统管理员身份，限制实际上传字节数并清理中断的上传。备份开始前按数据库物理大小和受管文件大小的五倍预检空间，另保留至少 512 MiB；恢复与更新分别预留原生 SQL 展开、旧库副本和事务所需空间。恢复 SQL 流按实际展开大小持续检查空间，上限为 `LEARNGRAPH_MAX_BACKUP_BYTES` 的四倍，超限不提交恢复事务。PostgreSQL 指纹查询仅暂存固定长度摘要，事务内 `work_mem` 限为 16 MiB；数据库专用更新备份不构造整站文件引用列表。PostgreSQL 自身磁盘上的 WAL/事务空间仍需独立保证；预检不能替代磁盘监控或阻止其他进程同时耗尽空间。

支持文件保存接口的浏览器先选择保存位置，再直接流式写入文件。其他浏览器及手机 App 使用已生成并完整校验的加密文件进行原生下载，同样无需整包 Blob 或 Base64。下载授权只绑定发起操作的管理员登录会话，十分钟有效且只能领取一次；浏览器使用 HttpOnly/SameSite Cookie，原生客户端可使用同一登录会话的 Bearer。服务端领取时重新校验管理员、租户、会话有效期和撤销状态；文件在下载结束、断开或过期时清理，重启也会补做过期清理。下载 URL 不含密码或可独立使用的授权密钥。旧的脱敏工作区 ZIP 不兼容全站恢复，解析器会明确拒绝。
